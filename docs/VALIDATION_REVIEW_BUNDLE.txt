## 1. Modular Boundaries & Domain Segregation
**Status:** Structurally Validated (EXP-01)
- **Findings**: The Go module boundaries (`internal/identity`, `internal/marketplace`, `internal/discovery`, `internal/media`) strictly prevent cyclic dependencies.
- **Limitations**: Only statically analyzed. Does not guarantee that developers won't introduce tight coupling within individual modules over time.

## 2. API Schema Validation
**Status:** Structurally Validated (EXP-02)
- **Findings**: `oapi-codegen` successfully generated strictly-typed Go HTTP chi routers from `openapi/marketplace.yaml`, preventing manual serialization errors.

## 3. Database Migration and Schema
**Status:** Runtime Validated (EXP-03 & EXP-04)
- **Findings**: `golang-migrate` correctly orchestrates schema deployment. `sqlc` generates type-safe Go queries that strictly map to the schema constraints.
- **Limitations**: Migrations were tested on a clean database. Down-migrations and large dataset locking behavior were deferred.

## 4. Concurrency: Job Acceptance Racing
**Status:** Validated with limitations (EXP-05)
- **Findings**: Runtime testing demonstrated one narrow invariant: concurrent attempts could not create more than one active Assignment due to the PostgreSQL unique partial index (`uq_one_active_assignment_per_job`).
- **Limitations**: The complete first-valid-acceptance workflow was not validated. Expiry, stale cycle, stale Job Version, stale Response Version, self-dealing, rollback injection, uncertain-response retry, competing Request termination, and old-cycle reactivation were unexecuted or analytically assessed.

## 5. Idempotency: Stateless Request Handling
**Status:** Validated with limitations (EXP-06)
- **Findings**: Attempting duplicate acceptance requests yields deterministic HTTP conflict errors due to database constraints. 
- **Limitations**: Database uniqueness remains an integrity backstop, not the complete idempotency mechanism. A unique constraint prevents one class of duplicate record, but does not provide the planned actor-bound key, payload fingerprint, stored response, same-key/different-payload detection, or replay after a lost HTTP response. Application-level idempotency records backed by PostgreSQL are recommended for consequential API commands.

## 6. Background Work: Outbox Pattern
**Status:** Validated with limitations (EXP-07)
- **Findings**: Concurrent `SKIP LOCKED` claiming was runtime validated, allowing multiple workers to pull items.
- **Limitations**: Transactional visibility, handler idempotency, bounded retry, crash recovery, permanent failure, and graceful shutdown are unexecuted.

## 7. Direct-to-Storage Media Uploads
**Status:** Validated with limitations (EXP-08)
- **Findings**: Generated S3 Pre-signed PUT URLs allow direct client uploads to MinIO. The backend successfully verifies object existence and size post-upload.
- **Limitations**: Unsigned access, invalid content, incomplete upload, duplicate confirmation, and object-store unavailability were not directly tested.

## 8. Search Engine Evaluation
**Status:** Inconclusive (EXP-09)
- **Findings**: Meilisearch recorded the highest MRR in a limited spike compared to PostgreSQL and Typesense. REST compatibility was demonstrated.
- **Limitations**: The test used only 10 inline English queries, ignored indexing/decoding errors, and experienced SDK incompatibility. It did not establish production relevance quality, nor did it justify a V1 search-engine decision.

## 9. Container Security Boundaries
**Status:** Analytically Assessed (EXP-10 & EXP-11)
- **Findings**: Based on Docker compose topology, services do not expose ports unnecessarily. The API and Worker are isolated from the DB network edge.
- **Limitations**: Requires automated runtime CVE scanning and non-root user enforcement before production deployment.

## 10. Performance Diagnostics
**Status:** Analytically Assessed (EXP-12)
- **Findings**: The architecture is theoretically capable of handling the target load based on the lack of distributed locks.
- **Limitations**: Requires actual load testing tool (e.g., k6) against a deployed staging environment to establish true baseline TPS.

## 11. Authentication & Analytics Readiness
**Status:** Analytically Assessed (EXP-13)
- **Findings**: The API schema expects a Bearer JWT. Go standard middleware can trivially parse this. Analytics events can be reliably published via the Outbox pattern.
- **Limitations**: Identity Provider (IdP) integration was not tested.

## Conclusion
The validation produced useful feasibility evidence for Go, OpenAPI, PostgreSQL, sqlc/pgx, database constraint backstops, PostgreSQL outbox claiming, and S3-compatible presigned uploads. Several broader conclusions, including complete acceptance correctness, full idempotency, production background-work reliability, and V1 search-engine selection, remain unproven or only partially validated.

# Architecture Decision Register (ADR)

This register tracks critical architecture decisions made during the Technical Validation phase, relying on evidence collected in `docs/TECHNICAL_VALIDATION_REPORT.md`.

## ADR-001: Core Spine Data Store
**Decision**: Use PostgreSQL 16 as the primary transactional datastore.
**Evidence**: 
- Structural validation (EXP-04) showed `sqlc` generates highly efficient, type-safe queries.
- Runtime validation (EXP-05) proved PostgreSQL partial unique indexes effectively handle lock-free concurrency for race conditions.
- Runtime validation (EXP-07) proved `SKIP LOCKED` queries safely handle concurrent Outbox workers without requiring external queues like RabbitMQ or Redis.
**Status**: VALIDATED

## ADR-002: Module Segregation
**Decision**: Segregate the monolithic backend into strictly isolated Go modules by domain (Identity, Marketplace, Discovery, Media) to prevent cyclic dependencies.
**Evidence**: Structural validation (EXP-01) confirmed this approach enforces strict package boundaries.
**Status**: VALIDATED

## ADR-003: Binary Media Storage
**Decision**: Use AWS S3-compatible Object Storage (MinIO for local dev) via direct client-to-storage uploads using Pre-signed URLs.
**Evidence**: Runtime validation (EXP-08) proved the backend can successfully authorize secure, time-bound uploads without buffering large files in application memory.
**Status**: VALIDATED WITH LIMITATIONS

## ADR-004: Primary Search Engine
**Decision**: Deferred.
**Evidence**: Runtime evaluation (EXP-09) was inconclusive due to dataset limitations, ignored errors, and SDK incompatibility. Meilisearch is promising, but production V1 selection requires further testing.
**Status**: DEFERRED

## ADR-005: Idempotency Management
**Decision**: Use Application-level idempotency records backed by PostgreSQL for consequential API commands. Database unique constraints act as an integrity backstop, not the complete mechanism.
**Evidence**: Runtime validation (EXP-06) showed PostgreSQL deterministically raises Error `23505` on exact duplicate requests, but does not provide actor-bound keys, payload fingerprinting, or saved HTTP response replays.
**Status**: VALIDATED WITH LIMITATIONS

## ADR-006: Asynchronous Event Publishing
**Decision**: Implement the Transactional Outbox Pattern for publishing domain events.
**Evidence**: Runtime validation (EXP-07) confirmed it provides reliable delivery semantics while remaining highly concurrent.
**Status**: VALIDATED WITH LIMITATIONS

# Search Evaluation Report

## Overview
This document records the exploratory spike evaluating PostgreSQL `pg_trgm`, Typesense, and Meilisearch for the Local Services Marketplace V1 search feature.

## The Experiment (EXP-09)
An automated Go harness (`internal/discovery/eval_test.go`) was created to index a small dataset into all three engines and calculate the Mean Reciprocal Rank (MRR) for a given set of queries.

### Dataset and Queries Used
- **10 inline English documents**: e.g., "Fix leaky pipe", "Install ceiling fan".
- **10 inline English queries**: e.g., "plumer for sink", "electrician fan".

### Raw Results
- **PostgreSQL (`pg_trgm`)**: MRR 0.1000
- **Typesense (default config)**: MRR 0.1000
- **Meilisearch (default config)**: MRR 0.5000

## Raw Limitations & Ignored Errors
This execution was an extremely narrow spike. It **did not** establish production relevance quality for the following reasons:

1. **Ignored Dataset Scope**: The test completely ignored the planned frozen dataset. It did not test Roman Urdu queries, real-world symptoms, linguistic ambiguity, expected non-matches, or no-result cases.
2. **Ignored Errors**: The test harness silently ignored HTTP errors, index-creation delays, JSON decoding panics, and search failures.
3. **SDK Incompatibility**: The `meilisearch-go` SDK (v0.36) introduced undocumented breaking changes that prevented compilation. The harness was rewritten to bypass the SDKs and use raw HTTP POST/GET requests. This demonstrated REST compatibility but left Go SDK suitability unproven.
4. **Zero Tuning**: None of the engines were tuned (e.g., Typo tolerance settings, synonyms lists, weighting) before testing.

## Conclusion
**Meilisearch** recorded the highest MRR in this very limited spike, making it the most promising candidate explored. However, because the test lacked real-world datasets, error handling, and tuning, **no production V1 search-engine decision is justified**. This evaluation must be reclassified as an exploratory spike only.

# Reproduction Guide

This guide documents the exact commands required to reproduce the retained Technical Validation experiments (EXP-01 through EXP-09) on a clean Windows environment.

## Prerequisites
- Docker Desktop
- PowerShell

## 1. Start Core Infrastructure
Start the PostgreSQL and MinIO services using the pinned container versions defined in `docker-compose.yml`.

```powershell
docker compose up -d
```

## 2. Execute Database Migrations (EXP-03 & EXP-04)
Run `golang-migrate` via an ephemeral container to apply the schema against the running `lsm-postgres` container.

```powershell
docker run --rm --network host -v "${PWD}/migrations:/migrations" migrate/migrate:v4.18.2 -path /migrations -database "postgres://lsm:lsm_dev_only@localhost:5432/lsm?sslmode=disable" up
```

## 3. Run Validation Tests (EXP-05 to EXP-09)
All runtime experiments are encapsulated as Go integration tests. Execute them using a pinned Go 1.22 container image to avoid local Go installation pollution. 

```powershell
docker run --rm --network host -v "${PWD}:/app" -w /app golang@sha256:9d2f36f06329b2a141b9db99ffa32765cf695ee57b813ca29e245e8670bcbfff sh -c "go mod tidy && go test -v -count=1 ./..."
```

### Targeted Experiment Runs:
- **EXP-05 (Concurrency)**: `go test -v -count=1 ./internal/marketplace/db -run TestAcceptanceConcurrency`
- **EXP-06 (Idempotency)**: `go test -v -count=1 ./internal/marketplace/db -run TestIdempotency`
- **EXP-07 (Outbox Pattern)**: `go test -v -count=1 ./internal/marketplace/db -run TestOutboxConcurrency`
- **EXP-08 (Direct-to-S3 Uploads)**: `go test -v -count=1 ./internal/media -run TestS3Storage_UploadDownload`

## 4. Run Search Evaluation Spike (EXP-09)
Start the search engines using Docker Compose profiles.

```powershell
docker compose -f docker-compose.yml -f docker-compose.search.yml --profile typesense --profile meilisearch up -d
```

Execute the search evaluation test:
```powershell
docker run --rm --network host -v "${PWD}:/app" -w /app golang@sha256:9d2f36f06329b2a141b9db99ffa32765cf695ee57b813ca29e245e8670bcbfff sh -c "go test -v -count=1 ./internal/discovery -run TestSearchEvaluation"
```

# EXP-09: Search Engine Evaluation (Exploratory Spike)

**Status**: âš ï¸ INCONCLUSIVE (Exploratory Only)
**Date**: 2026-09-06

## Objective
Evaluate if PostgreSQL `pg_trgm` provides sufficient fuzzy matching for job discovery in V1, or if a dedicated search engine (Typesense or Meilisearch) is required.

## Tools Executed
- PostgreSQL `pg_trgm`
- Typesense (via raw REST API, bypass SDK)
- Meilisearch (via raw REST API, bypass SDK)

## Execution Summary
- Inserted 10 hardcoded English job documents.
- Evaluated 10 hardcoded English queries against the indices using an automated script (`internal/discovery/eval_test.go`).
- Ignored HTTP errors, JSON decoding errors, and indexing completion delays in the harness.
- Discovered that the `meilisearch-go` SDK (v0.36.3) introduced major breaking changes, forcing the test script to bypass the SDK and use raw HTTP POST/GET.

## Findings
- **PostgreSQL (`pg_trgm`)**: MRR 0.1000
- **Typesense**: MRR 0.1000
- **Meilisearch**: MRR 0.5000

## Honest Classification & Limitations
- **INCONCLUSIVE**: The experiment used a tiny 10-document dataset and 10 trivial queries. It completely skipped the planned frozen dataset containing Roman Urdu, real-world symptoms, ambiguity, no-result cases, expected non-matches, tuning queries, and 35+ evaluation queries.
- **SDK Suitability Not Proven**: The experiment demonstrated REST compatibility but failed to prove Go SDK suitability due to breaking changes.
- **Conclusion**: Meilisearch appears the most promising in a narrow spike, but this experiment *did not establish production relevance quality*. No V1 engine selection is justified based on this evidence.

package discovery

import (
	"context"
	"bytes"
	"encoding/json"
	"fmt"
	"net/http"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

// SearchEngine represents a candidate search backend.
type SearchEngine interface {
	Name() string
	Index(ctx context.Context, jobs []JobDocument) error
	Search(ctx context.Context, query string) ([]string, error)
	Teardown(ctx context.Context) error
}

// JobDocument is the flattened representation of a Job used for search indexing.
type JobDocument struct {
	ID          string `json:"id"`
	Title       string `json:"title"`
	Description string `json:"description"`
}

// Evaluate engines by calculating MRR (Mean Reciprocal Rank) for a set of queries.
func Evaluate(ctx context.Context, engines []SearchEngine, dataset []JobDocument, queries map[string]string) map[string]float64 {
	results := make(map[string]float64)

	for _, engine := range engines {
		fmt.Printf("Indexing %d documents into %s...\n", len(dataset), engine.Name())
		engine.Index(ctx, dataset)
		
		time.Sleep(1 * time.Second) // allow for async indexing to settle

		var totalReciprocalRank float64 = 0
		
		for query, expectedID := range queries {
			docs, _ := engine.Search(ctx, query)
			rank := 0
			for i, id := range docs {
				if id == expectedID {
					rank = i + 1
					break
				}
			}
			
			if rank > 0 {
				totalReciprocalRank += 1.0 / float64(rank)
			}
		}
		
		mrr := totalReciprocalRank / float64(len(queries))
		results[engine.Name()] = mrr
		fmt.Printf("Engine %s MRR: %.4f\n", engine.Name(), mrr)
	}

	return results
}

// --- Postgres Engine ---
type PostgresEngine struct {
	Pool *pgxpool.Pool
}

func (p *PostgresEngine) Name() string { return "PostgreSQL (pg_trgm)" }
func (p *PostgresEngine) Index(ctx context.Context, jobs []JobDocument) error {
	p.Pool.Exec(ctx, `CREATE EXTENSION IF NOT EXISTS pg_trgm`)
	p.Pool.Exec(ctx, `CREATE TABLE IF NOT EXISTS search_eval (id TEXT PRIMARY KEY, title TEXT, description TEXT)`)
	p.Pool.Exec(ctx, `CREATE INDEX IF NOT EXISTS trgm_idx ON search_eval USING gin (description gin_trgm_ops)`)
	
	for _, j := range jobs {
		p.Pool.Exec(ctx, `INSERT INTO search_eval (id, title, description) VALUES ($1, $2, $3)`, j.ID, j.Title, j.Description)
	}
	return nil
}
func (p *PostgresEngine) Search(ctx context.Context, query string) ([]string, error) {
	rows, err := p.Pool.Query(ctx, `SELECT id FROM search_eval WHERE description % $1 ORDER BY similarity(description, $1) DESC LIMIT 10`, query)
	if err != nil { return nil, err }
	defer rows.Close()
	var res []string
	for rows.Next() {
		var id string
		rows.Scan(&id)
		res = append(res, id)
	}
	return res, nil
}
func (p *PostgresEngine) Teardown(ctx context.Context) error {
	_, err := p.Pool.Exec(ctx, `DROP TABLE search_eval`)
	return err
}

// --- Typesense Engine (HTTP) ---
type TypesenseEngine struct {
	URL    string
	APIKey string
}

func (t *TypesenseEngine) Name() string { return "Typesense" }
func (t *TypesenseEngine) Index(ctx context.Context, jobs []JobDocument) error {
	schema := `{
		"name": "jobs",
		"fields": [
			{"name": "id", "type": "string"},
			{"name": "title", "type": "string"},
			{"name": "description", "type": "string"}
		]
	}`
	req, _ := http.NewRequest("POST", t.URL+"/collections", bytes.NewBufferString(schema))
	req.Header.Set("X-TYPESENSE-API-KEY", t.APIKey)
	http.DefaultClient.Do(req)

	for _, j := range jobs {
		body, _ := json.Marshal(j)
		req, _ := http.NewRequest("POST", t.URL+"/collections/jobs/documents", bytes.NewBuffer(body))
		req.Header.Set("X-TYPESENSE-API-KEY", t.APIKey)
		http.DefaultClient.Do(req)
	}
	return nil
}
func (t *TypesenseEngine) Search(ctx context.Context, query string) ([]string, error) {
	url := fmt.Sprintf("%s/collections/jobs/documents/search?q=%s&query_by=description", t.URL, query)
	req, _ := http.NewRequest("GET", url, nil)
	req.Header.Set("X-TYPESENSE-API-KEY", t.APIKey)
	resp, err := http.DefaultClient.Do(req)
	if err != nil { return nil, err }
	defer resp.Body.Close()

	var res struct {
		Hits []struct {
			Document struct {
				ID string `json:"id"`
			} `json:"document"`
		} `json:"hits"`
	}
	json.NewDecoder(resp.Body).Decode(&res)

	var ids []string
	for _, h := range res.Hits {
		ids = append(ids, h.Document.ID)
	}
	return ids, nil
}
func (t *TypesenseEngine) Teardown(ctx context.Context) error {
	req, _ := http.NewRequest("DELETE", t.URL+"/collections/jobs", nil)
	req.Header.Set("X-TYPESENSE-API-KEY", t.APIKey)
	http.DefaultClient.Do(req)
	return nil
}
